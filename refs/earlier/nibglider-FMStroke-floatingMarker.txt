GEOMETRIC SEMANTIC HIERARCHY

NGPath should be the general editable path representation.  It may be a
regular Bezier path, b-spline, composite path, or smoothed polyline.  Shape
objects should be a semantic geometric layer above NGPath, with parameters
that preserve what the user intended rather than only the resulting points.

    NGPath
        > Shape
            > Polygon
                > RegularPolygon
                > Quadrilateral
                    > Rectangle
                    > Parallelogram
                    > Trapezoid
                    > Rhombus
                    > Kite
                > Triangle
                    > RightTriangle
                    > RegularTriangle
                    > Trigon
            > Circle / Ellipse
            > Supershape
            > Arc

The hierarchy is for editable geometric meaning, not necessarily for the
rendering objects.  For example, a Rectangle stores its origin, dimensions,
rotation, and aspect-ratio constraint; a RegularPolygon stores side count,
radius convention, and rotation; a Trapezoid stores its frame and angle.
These values generate a derived NGPath/Paper.js path for display and export.

The program should preserve the semantic shape while its defining invariants
remain true.  Direct edits can either update the relevant parameters or,
when they no longer describe the resulting geometry, explicitly convert the
item to a regular NGPath.

Boolean operations are a required conversion boundary:

    semantic shape + union / subtraction / intersection
        -> evaluate derived geometry
        -> resulting regular NGPath or compound path

The boolean result ordinarily cannot remain a Rectangle, Polygon,
Parallelogram, or other constrained shape because its geometry may no longer
satisfy that type's invariants.  The result should therefore retain ordinary
editable path geometry, but not falsely retain the original semantic shape
identity or parameters.  The user can later use a "recognize / convert to
shape" operation if the resulting path happens to satisfy a known geometry.

NGPath composite stroke semantics follow the same rule.  An NGPath in
`ngComposite` mode stores meaningful point/corner and outgoing-segment
conventions; it derives Bezier geometry for display/export.  Operations that
destroy a one-to-one relationship with those conventions should convert it to
a regular Bezier NGPath unless an operation has an explicitly defined
semantic-preservation rule.

In TypeScript this does not require a deep runtime class inheritance tree.
A discriminated semantic geometry model with a common `toNGPath()` /
`toRenderablePath()` interface gives the same geometric hierarchy while
remaining serializable, testable, and compatible with Paper.js.  Paper.js
items remain derived scene/render objects, not the authoritative geometric
model.
